## Overview

In F-Mesh, the data exchanged between components is represented as **signals** — flexible units of information that can carry any type of payload. Signals serve as the foundation for communication within the mesh, enabling the dynamic flow of data between components. 

Each signal consists of two elements:
1. **Payload** - The actual data being transferred (can be any Go type)
2. **Metadata** - Optional key-value entries (string or numeric values) for categorization, filtering and routing

To explore the full capabilities of signals, refer to the [signal package API](https://pkg.go.dev/github.com/hovsep/fmesh/signal).

## Immutability (copy-on-write)

Signals are **immutable**. Mutating methods such as `WithMeta`, `WithMetaMany`, or `MapPayload` return a **new** signal; the original is never modified. This is important when signals are fanned out through pipes — multiple ports may share the same signal pointer, and immutability prevents one component from corrupting another's view of the data.

```go
original := signal.New("hello")
tagged := original.WithMeta("source", "sensor1")

// original is unchanged
original.Meta().Has("source") // false
tagged.Meta().Has("source")   // true
```

When you need to modify a signal that may be shared, always assign the result of a `With*` method:

```go
sig = sig.WithMeta("processed", "true")
```

## Payload

The payload of a signal can be any valid Go data type, offering immense flexibility. This includes primitive types like integers and strings, complex types like structs and maps, or even nil.

It's important to note that **every signal in F-Mesh always has a payload**, even if that payload is nil. There is no concept of an "empty" signal, ensuring consistency in data handling across the mesh.

Example of creating a simple signal:

```go
mySignal := signal.New("example payload") // A signal with a string payload
```

## Reading typed payloads

A payload is `any`, because a mesh carries mixed types down one pipe. Every component that reads one therefore has to get it back out, and a bare type assertion is either unchecked — panicking the whole run when something upstream changes its payload type — or checked, and three lines every time. `Signal` has two generic methods instead:

```go
// Reports what went wrong; never panics
temperature, err := sig.As[float64]()
if err != nil {
    return err
}

// Carries on with a default when the payload is missing or of another type
retries := sig.PayloadOrDefault(0)
```

Both are safe on a nil `*Signal`, which is what `Group.First()` returns for an empty group, so the usual read from a port is one chain:

```go
n, err := this.InputByName("in").Signals().FirstAs[int]()   // ErrNoSignalsInGroup when empty
n := this.InputByName("in").Signals().FirstPayloadOrDefault(0)   // default when empty or wrong type
```

`As` fails rather than panicking on purpose: a component reading a payload it did not produce cannot know that something upstream changed, and finding out by taking down the mesh is not a useful way to be told. A nil signal and a nil payload are both handled — the fallible form returns an error, the defaulting form returns the default.

> [!WARNING]
> **Prefer `As`.** `PayloadOrDefault` cannot tell "wrong type" from "genuinely absent", and it reports
> neither. A producer that changes from `int` to `int64` compiles, runs, and quietly feeds `0` to
> everything downstream — no error, no log line, just a wrong answer. Reach for `PayloadOrDefault` only
> where the default is the correct answer for a wrong type, not merely the convenient one.

```go
// Upstream changed int -> int64. This keeps running:
price := sig.PayloadOrDefault(0)   // 0
// This says what happened:
price, err := sig.As[int]()   // "signal payload is int64, not int"
```

There are no per-type shorthands such as `AsInt`: `sig.As[int]()` is already as short, and `PayloadOrDefault` infers the type from the default you pass:

```go
sig.PayloadOrDefault(0)     // int
sig.PayloadOrDefault("")    // string
sig.PayloadOrDefault(false) // bool
```

> [!IMPORTANT]
> One catch: an untyped `0` infers `int`, so `sig.PayloadOrDefault(0)` on a **float64** payload quietly returns `0` rather than the payload. Pass `0.0`, or use `sig.Float64OrDefault(0)` — the one defaulting shorthand that exists, for exactly this reason.

`sig.AsGroup()` is for a signal whose payload is another `signal.Group` — see [Signal Groups](#signal-groups) below.

### AsNumber

`sig.AsNumber()` returns `(float64, bool)` and is the loose one. It accepts `float64`, `float32`, `int`, `int64` and `uint64`, and encodes `bool` as `1` and `0`:

```go
if value, ok := sig.AsNumber(); ok {
    // the signal carries a measurement
}
```

It exists for the code that has to decide whether a signal is a measurement **at all**. A structured signal commonly uses its payload as a type tag — `"air"`, `"venous_blood"` — and keeps the real values in [metadata](#metadata), so anything drawing or logging a mesh needs to tell a number from a name without knowing which components produce which.

## Signal Groups

While individual signals are useful for most cases, there are scenarios where working with a **group of signals** simplifies the design. A signal group aggregates multiple signals, each potentially carrying a different type of payload.

```go
// Create a group from multiple payloads
mySignals := signal.NewGroup(1, nil, 3, []int{4, 5, 6}, map[byte]byte{7: 8})

// Work with signals in a port (also a group)
port.Signals().Filter(signal.HasMeta("priority"))
```

Signal groups are part of F-Mesh's consistent Collections and Groups API. For complete documentation on filtering, iterating, and working with groups, see the [Collections and Groups page](https://github.com/hovsep/fmesh/wiki/203.-Collections-and-Groups).

## Metadata

Signals can be tagged with **metadata** — key-value entries that describe the signal without affecting the payload. A value is a `string` or a `float64`, chosen per entry. Metadata is useful for categorization, filtering, routing, weights and debugging.

Because signals are copy-on-write, use `With*` methods and assign the result:

```go
// Create signal with metadata
sig := signal.New("measurement").WithMetaMany(map[string]string{
    "priority": "high",
    "source":   "sensor1",
})

// Or add entries one at a time — strings and numbers share one store
sig = sig.WithMeta("priority", "high").WithMeta("weight", 0.85)

// Query — the read names its type, or infers it from the default
if sig.Meta().ValueIs("priority", "high") {
    // Handle high priority signal
}
weight := sig.Meta().ValueOrDefault("weight", 0.0)

// Filter signals using predicate helpers
highPriority := port.Signals().Filter(signal.MetaEquals("priority", "high"))
```

Metadata is preserved when signals flow through pipes and works the same way on components, ports and the mesh. For the full store API, see the [Metadata page](https://github.com/hovsep/fmesh/wiki/202.-Metadata).

Signal groups support batch metadata on their contents (`WithMetaOnEach`, `WithoutMetaOnEach`) — see the [Collections and Groups page](https://github.com/hovsep/fmesh/wiki/203.-Collections-and-Groups).

## Predicate helpers

The `signal` package provides composable predicate helpers for filtering:

```go
port.Signals().Filter(signal.And(
    signal.HasMeta("priority"),
    signal.MetaEquals("priority", "high"),
))

port.Signals().Filter(signal.Or(
    signal.MetaEquals("source", "sensor1"),
    signal.MetaEquals("source", "sensor2"),
))
```

Available helpers: `Not`, `And`, `Or`, `HasMeta`, `HasAnyMeta`, `MetaEquals`, `MetaContains`.

## Metadata copy-on-write API

| Method | Description |
|--------|-------------|
| `WithMeta(key, value)` | Add or update one entry (string or float64) |
| `WithMetaMany(map)` | Add or update many |
| `WithoutMeta(keys...)` | Remove specific entries |

## Advanced signal.Group operations

Beyond `Filter` and `Map`, groups support:

| Method | Description |
|--------|-------------|
| `With(signals...)` / `WithPayloads(...)` / `Join(other)` | Build new groups |
| `Contains(sig)` / `ContainsPayload(v)` | Membership checks; `ContainsPayload` takes any comparable `v` — use `ContainsPayloadFunc` for slices and maps |
| `MapPayloads(mapper)` / `MapPayloadsIf(pred, mapper)` | Transform payloads, preserve metadata |
| `Reduce(initial, fn)` / `ReducePayloads(initial, fn)` | Fold group into single signal or value; `ReducePayloads` is generic in the accumulator type |
| `FirstAs[T]()` / `FirstPayloadOrDefault(d)` | First payload as `T`, with an error or a default (see [Reading typed payloads](#reading-typed-payloads)) |
| `ForEachIf(pred, action)` | Iterate matching signals only |
| `Every(pred)` / `Any(pred)` / `Count(pred)` | Predicate queries |

### Function types

| Type | Signature | Used by |
|------|-----------|---------|
| `Predicate` | `func(*Signal) bool` | `Filter`, `Any`, `Every` |
| `Mapper` | `func(*Signal) *Signal` | `Map`, `MapIf` |
| `PayloadMapper` | `func(any) any` | `MapPayload`, `MapPayloads` |
| `Reducer` | `func(acc, s *Signal) *Signal` | `Reduce` |

## Signal errors

| Error | When |
|-------|------|
| `ErrNoSignalsInGroup` | `FirstPayload()` / `FirstAs[T]()` on empty group |

`Payload()` always succeeds on a valid signal; `FirstPayload()` returns an error on empty groups.
