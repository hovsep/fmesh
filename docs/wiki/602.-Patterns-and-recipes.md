The earlier pages explain how F-Mesh works. This page collects proven ways to structure a mesh.

## Topology patterns

### Linear pipeline with a generic builder

For a chain of similar stages, don't wire each pipe by hand. Write a builder that gives every
component `in`/`out` ports, tags it with a `stage` entry, and pipes stage *N* to stage *N+1*:

```go
func buildPipeline(name string, components ...*component.Component) (*fmesh.FMesh, error) {
    for i, c := range components {
        c.Meta().Set("stage", strconv.Itoa(i+1))
        if err := c.AddInputs("in"); err != nil { return nil, err }
        if err := c.AddOutputs("out"); err != nil { return nil, err }
        if i > 0 {
            if err := components[i-1].OutputByName("out").PipeTo(c.InputByName("in")); err != nil {
                return nil, err
            }
        }
    }
    // ... fmesh.New + AddComponents ...
}
```

The `stage` entry finds the entry point by role, not by name:

```go
first := fm.Components().FindAny(func(c *component.Component) bool {
    return c.Meta().ValueIs("stage", "1")
})
err := first.InputByName("in").PutSignals(signal.New("start"))
```

### Broadcast bus

A star: every node talks to every other node through a central bus. Wire each node both ways
(`node.tx → bus.rx`, `bus.tx → node.rx`). The bus is one line:

```go
component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
    return port.ForwardSignals(ctx, this.InputByName("rx"), this.OutputByName("tx"))
})
```

Every node receives everything and keeps what is addressed to it — by an address in its
[state](https://github.com/hovsep/fmesh/wiki/301.-Component#stateful-component) or by signal
metadata. Adding a node never changes existing wiring.

### Fan-in and reduce

When many producers pipe into **one input port**, the port collects one signal per producer per
cycle. The consumer reads the whole group and reduces it:

```go
readings := make([]float64, 0, this.InputByName("in").Signals().Len())
_ = this.InputByName("in").Signals().ForEach(func(sig *signal.Signal) error {
    readings = append(readings, sig.Float64OrDefault(0))
    return nil
})
combined := slices.Min(readings) // or sum, average, majority vote…
```

This models shared-medium effects well (arbitration, interference, voting). If a component
expects exactly one signal, check it: `Signals().Len() > 1` usually means a wiring bug.

### Content-based routing

Give the router one output per destination and decide per signal. Metadata makes a good routing key:

```go
component.WithOutputs("passed", "dropped"),
component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
    return this.InputByName("in").Signals().ForEach(func(sig *signal.Signal) error {
        if sig.Meta().ValueIs("genre", "pop") {
            return this.OutputByName("dropped").PutSignals(sig)
        }
        return this.OutputByName("passed").PutSignals(sig)
    })
})
```

`ForEachIf(predicate, action)` and `port.ForwardWithFilter(ctx, src, dst, predicate)` say the same
thing more briefly — see [Conditional forwarding](https://github.com/hovsep/fmesh/wiki/303.-Pipes#conditional-forwarding).

### Load balancer (dispatch and collect)

[Indexed ports](https://github.com/hovsep/fmesh/wiki/301.-Component#indexed-ports) give a numbered
port per worker. Component state holds the round-robin cursor:

```go
lb, err := component.New("lb",
    component.WithInputs("in"), component.WithOutputs("out"),
    component.WithIndexedOutputs("downstream", 0, numWorkers-1), // to workers
    component.WithIndexedInputs("upstream", 0, numWorkers-1),    // from workers
    component.WithInitialState(func(s component.State) { s.Set("next", 0) }),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        next := this.State().GetOrDefault("next", 0).(int)
        _ = this.InputByName("in").Signals().ForEach(func(sig *signal.Signal) error {
            out := fmt.Sprintf("downstream%d", next%numWorkers)
            next++
            return this.OutputByName(out).PutSignals(sig)
        })
        this.State().Set("next", next)
        // collect worker responses into the single output
        for i := range numWorkers {
            in := this.InputByName(fmt.Sprintf("upstream%d", i))
            _ = port.ForwardSignals(ctx, in, this.OutputByName("out"))
        }
        return nil
    }))
```

The cursor lives in state, so distribution stays fair across many `Run` calls.

## Feedback loops and generators

### Generator via loopback

A component whose outputs feed its own inputs becomes an iterative process. Cycles drive the
iteration; the loop state travels through the ports:

```go
_ = gen.LoopbackPipe("o_prev", "i_prev")
_ = gen.LoopbackPipe("o_cur", "i_cur")

// seed the loop before Run
_ = gen.InputByName("i_prev").PutSignals(signal.New(0))
_ = gen.InputByName("i_cur").PutSignals(signal.New(1))
```

### Emit to continue, stay silent to stop

A loop runs only while signals keep arriving. There is no "stop" call. A component ends the loop
**by not emitting into it**:

```go
if next >= limit {
    return nil // no output ⇒ no next activation ⇒ the mesh stops
}
return this.OutputByName("o_cur").PutSignals(signal.New(next))
```

This rule covers every cyclic topology. A loop that always emits runs until the cycle or time
limit. The default limits are a safety net while you develop.

### Kick-start port

When a loop needs a one-time trigger, give one component a `bootstrap` input. Seed it before
`Run` and branch on it:

```go
if this.InputByName("bootstrap").HasSignals() {
    // first activation: start the loop, skip the normal logic
    return this.OutputByName("request").PutSignals(signal.New(initialValue))
}
// steady state: react to the loop input, re-emit (or stay silent to stop)
```

### Heartbeat and countdown

A component that re-emits into its own loopback activates every cycle. Use it for watchdogs,
timers and startup sequences:

```go
_ = watchdog.LoopbackPipe("keepalive", "keepalive")
// inside the activation function:
if !meshIsIdle {
    return this.OutputByName("keepalive").PutSignals(signal.New(true))
}
return nil // stop emitting ⇒ the mesh goes quiet
```

For a countdown, seed `N` and re-emit `N-1` while it is positive. The component then runs for
exactly N cycles.

### Breaking a cycle of dependencies

If A needs B's output *and* B needs A's, neither can go first within one tick. Fix: the stateful
side **publishes its stored value first**, then folds the new inputs into state for the next tick.
This costs one tick of latency:

```go
// A tick arrived: publish the stored value now, so others can proceed.
if this.InputByName("time").HasSignals() {
    level := this.State().GetOrDefault("level", 0.0).(float64)
    _ = this.OutputByName("level").PutSignals(signal.New(level))
}
// Updates from peers arrived: fold them into state for the next tick.
if this.InputByName("updates").HasSignals() {
    // ...update this.State()...
}
```

## Driving a mesh over time

### One mesh, many runs

`Run` cycles until no component activates, then returns. The mesh object survives:

- component state persists;
- input signals persist until consumed;
- output ports are cleared at the start of each `Run`;
- a failed run leaves its unconsumed inputs, and they join the next run's seed.

So a long-lived program can loop: put inputs, `Run`, read outputs, repeat.

```go
for job := range jobs {
    _ = worker.InputByName("in").PutSignals(signal.New(job))
    if _, err := fm.Run(ctx); err != nil { return err }
    results <- worker.OutputByName("out").Signals().AllPayloads()
}
```

Use `WithUnlimitedTime()` / `WithUnlimitedCycles()` when one run may be slow (for example, network
I/O inside an activation function).

### Tick-driven simulation

For discrete-time simulations, make the tick a signal. A `BeforeRun` hook puts it into a clock
component, and pipes deliver it to every component that needs time:

```go
fm.SetupHooks(func(h *fmesh.Hooks) {
    h.BeforeRun(func(ctx context.Context, mesh *fmesh.FMesh) error {
        tick := signal.New("tick").WithMeta("seq", float64(seq)).WithMeta("delta_t_ms", 10.0)
        return mesh.ComponentByName("clock").InputByName("ctl").PutSignals(tick)
    })
})
```

Carry the tick's fields (sequence number, Δt) as numeric
[metadata](https://github.com/hovsep/fmesh/wiki/202.-Metadata). One `Run` = one tick; call `Run`
in a loop to advance the clock.

### Interactive stepping

You can step a mesh from a REPL, a UI or a network endpoint. Two rules:

- **One goroutine owns the mesh.** Only it puts signals, runs and reads. The mesh is not safe for
  concurrent use from outside. Other goroutines send it work over a channel — a channel of
  closures works well:

```go
commands := make(chan func(fm *fmesh.FMesh))

// the owner:
for cmd := range commands {
    cmd(fm)            // e.g. put a signal, read state
    _, _ = fm.Run(ctx) // advance one step
}

// any other goroutine:
commands <- func(fm *fmesh.FMesh) {
    _ = fm.ComponentByName("source").InputByName("in").PutSignals(signal.New("hello"))
}
```

- **Detect idle steps** with the [run report](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run),
  so you can wait instead of spinning:

```go
ri, _ := fm.Run(ctx)
if ri.Cycles.Count(func(c *cycle.Cycle) bool { return c.HasActivatedComponents() }) == 0 {
    // nothing happened — wait for the next command
}
```

## Structuring a large mesh

### Component factories

Give each component a constructor returning `(*component.Component, error)`, and wrap errors at
each step. `main` then assembles the mesh from factories and holds no wiring detail. For families
of similar components, parameterize the factory (`newWorker(i int)`) and add them in bulk:
`fm.AddComponents(workers...)`.

### Subsystem structs

Group related components in a plain Go struct that knows how to list and connect them:

```go
type Node struct {
    Controller, Transmitter, Receiver *component.Component
}

func (n *Node) AllComponents() []*component.Component { /* ... */ }
func (n *Node) ConnectTo(bus *Bus) error              { /* internal + bus wiring */ }
```

`main` stays short: build nodes, `fm.AddComponents(node.AllComponents()...)`, `node.ConnectTo(bus)`.

### Nested mesh as a component

A whole mesh can hide behind one component that runs it — see
[Nested meshes](https://github.com/hovsep/fmesh/wiki/301.-Component#nested-meshes). Split the
wrapper's activation into phases:

1. **validate** — wait (keeping inputs) until all required inputs are present;
2. **sense** — forward the wrapper's inputs into the inner mesh;
3. **act** — `inner.Run(ctx)`;
4. **feedback** — forward the inner outputs to the wrapper's outputs.

`component.Sequential` expresses these phases: `component.RequireInputs` validates, and
`port.MultiForward` does sense and feedback.

Build the inner mesh **once** (in the wrapper's factory), not on every activation. Its component
state then persists across ticks. See
[Composing activation functions](https://github.com/hovsep/fmesh/wiki/301.-Component#composing-activation-functions).

### Convention-based wiring

With many components, explicit pipe lists get long. Pick a port-naming convention and wire by
lookup. For example, pipe the clock's output to every component with an input named `time`. Keep
port names as constants in one package.

Collect the edges into a `[]port.Pipe` and pass them to `port.MultiPipe(edges...)`. A name that
does not match gives a nil port, and `MultiPipe` reports that edge by name instead of panicking
later.

### Table-driven activation functions

When components differ only in data, build the activation function from a table:

```go
func activationFromTable(handlers map[string]func(*component.Component, *signal.Signal) error) component.ActivationFunc {
    return func(ctx context.Context, this *component.Component) error {
        return this.InputByName("in").Signals().ForEach(func(sig *signal.Signal) error {
            if handler, ok := handlers[sig.Meta().ValueOrDefault("cmd", "")]; ok {
                return handler(this, sig)
            }
            return nil // ignore unknown commands
        })
    }
}
```

A table splits an activation by **data**. To split it by **phase** (guard, compute, publish), use
the combinators — see [Composing activation functions](https://github.com/hovsep/fmesh/wiki/301.-Component#composing-activation-functions).

## Metadata techniques

See [Metadata](https://github.com/hovsep/fmesh/wiki/202.-Metadata) for the API.

- **Route by metadata.** Filters check `sig.Meta().ValueIs(k, v)`; a relay forwards only signals tagged for it.
- **Find components by role.** `fm.Components().FindAny(...)` over entries like `role=aggregator` keeps orchestration code free of component names.
- **Pack numeric fields as metadata** when you want them queryable: `signal.New("tick").WithMeta("seq", 1.0).WithMeta("delta_t_ms", 10.0)`. Use a struct payload when the mesh does not need to look inside. Unit-test each pack/unpack pair.
- **Tag the source when merging:**
  `port.ForwardWithMap(ctx, src, dst, func(s *signal.Signal) *signal.Signal { return s.WithMeta("from", name) })`.
  One collector port can then carry signals from many sources.
- **Tag a whole group:** `signal.NewGroup(payloads...).WithMetaOnEach("to", "usb")`, then `PutSignalGroups(...)`.

## Observing a running mesh

### Aggregator component

Instead of reading many components, add one *aggregator* that receives every observable port and
re-emits on one output. Tests and UIs then read one component. You can create its ports from a
list of `"component::port"` paths when you build the mesh.

### Streaming to the outside world

External consumers (TUIs, dashboards) should never touch the mesh. Publish from an `AfterRun`
hook to a sink:

```go
fm.SetupHooks(func(h *fmesh.Hooks) {
    h.AfterRun(func(ctx context.Context, mesh *fmesh.FMesh) error {
        return mesh.ComponentByName("publisher").OutputByName("stream").Signals().
            ForEach(func(line *signal.Signal) error {
                return sink.Publish(line.PayloadOrDefault(""))
            })
    })
})
```

Put the sink behind a small interface (`Publish(line string) error`), so stdout, a socket or a
no-op can swap. Make it **non-blocking and lossy** (buffered channel, drop and count on overflow),
so a slow observer never slows the mesh.

### Error side-channels

Give fallible components an `errors` output port, piped to a collector. On a per-item failure,
emit to that port and continue. Returning an error stops the whole mesh under the default
strategy, so keep it for truly fatal conditions.

## Testing patterns

[`MaybeActivate`](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run#testing-a-component-in-isolation)
tests one component. For whole-mesh behavior, use **hooks as probes**:

- **Collect a time series** with a component `AfterActivation` hook (or a mesh `AfterRun` hook that reads the aggregator).
- **Assert properties, not exact values**: the clock only grows, a value oscillates, values stay within bounds *and don't stick to a clamp boundary*. These survive timing noise; exact values don't.
- **Bound simulated time, not wall time.** A hook on the clock watches simulated time and triggers shutdown at the target. Guard the trigger with `sync.Once`.
- **Unit-test signal-packing helpers** (round trips, invariants such as "shares sum to 100%") apart from the mesh.

## Field-tested gotchas

- **A component activates when *any* input has signals.** If a phase must run once per tick, gate it on one port: `if !this.InputByName("time").HasSignals() { return nil }`.
- **`return nil` vs waiting.** `return nil` on partial input consumes what arrived. `component.ErrWaitKeepingInputs` keeps it until the rest arrives. See [Waiting for inputs](https://github.com/hovsep/fmesh/wiki/301.-Component#waiting-for-inputs).
- **Don't rely on activation order within a cycle.** Components run concurrently. If one value must come "before" another, carry it in state across ticks (see [Breaking a cycle of dependencies](#breaking-a-cycle-of-dependencies)).
- **Read payloads with `As[T]()`** at trust boundaries. Treat a wrong type as a data error (send it to an error port), not a panic.
- **Signals are shared pointers.** Treat payloads as read-only; see [Caveats](https://github.com/hovsep/fmesh/wiki/603.-Caveats#payloads-are-shared-between-destinations).
- **Outputs are cleared at the start of each `Run`; inputs persist.** Read outputs after a run. Seed through input ports or component state, never by filling outputs.
