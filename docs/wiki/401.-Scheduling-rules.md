This page describes what `Run(ctx)` does and when it stops. To read the results of a run
(`RuntimeInfo`, per-cycle results), see [Inspecting a run](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run).

## What happens when you call Run()

1. You build the mesh, connect pipes, and put initial signals on input ports.
2. You call `Run(ctx)`. It **blocks** until the mesh stops.
3. Each cycle, every component with at least one input signal activates. Ready components run **concurrently**.
4. After the cycle, output signals move through pipes to downstream input ports.
5. When `Run` returns, you read results from output ports.

There is no background goroutine. The mesh runs only while `Run` runs.

## When Run() stops

| Reason | Error |
|--------|-------|
| No component has input signals | `nil` (natural stop) |
| The cycle limit is reached (`WithCyclesLimit`) | `ErrReachedMaxAllowedCycles` |
| The time limit is exceeded (`WithTimeLimit`) | `ErrTimeLimitExceeded` |
| The caller's context is canceled | `ErrRunCanceled` |
| No progress (livelock) | `ErrLivelockDetected` |
| Error or panic under `StopOnFirstErrorOrPanic` | `ErrHitAnErrorOrPanic` |
| Panic under `StopOnFirstPanic` | `ErrHitAPanic` |
| A drain or hook failure | the wrapped error |

Defaults: **1000 cycles** and **5 seconds**. Remove them for long runs:

```go
fm, err := fmesh.New("long-running",
    fmesh.WithUnlimitedCycles(),
    fmesh.WithUnlimitedTime(),
)
```

The time limit becomes a deadline on the context that activation functions receive. A function that
respects its context stops at the deadline. A function that ignores it runs to the end: a running
cycle is never interrupted.

All options are listed in [Mesh configuration](https://github.com/hovsep/fmesh/wiki/601.-Tips-&-tricks).

**The last cycle is not drained when the run stops early.** `Run` checks whether to stop *before*
it moves signals through pipes. So when it stops for any reason other than a natural stop (an
error, a limit, a livelock, a cancel), the outputs of the last cycle stay on the output ports and
never reach downstream inputs. Read them there if you need them. See also
[A stopping error discards its siblings' work](https://github.com/hovsep/fmesh/wiki/603.-Caveats#a-stopping-error-discards-its-siblings-work).

## Running a mesh again

A mesh can run many times, but **one `Run` at a time**: never call `Run` again before the previous
call returned, and never from two goroutines.

At the start of every `Run`:

| What | Between runs |
|------|--------------|
| Output ports | **Cleared** |
| Input ports | **Kept.** Signals left by a failed or interrupted run become part of the next run's seed |
| `RuntimeInfo` | New for each run |
| Component `State()` | **Kept**. Call `ResetState()` to start fresh |
| Metadata, hooks, plugins | Kept |

To start a rerun clean after a failure, clear the inputs first:

```go
for _, c := range fm.Components().AllOrdered() {
    if err := c.ClearInputs(ctx); err != nil {
        return err
    }
}
```

## Ordering guarantees

A mesh is **deterministic**: the same input gives the same output, if your activation functions
are deterministic too. Three rules make this true.

**1. Signals on one port keep their arrival order.**

```go
_ = in.PutSignals(signal.New(1))
_ = in.PutSignals(signal.New(2))
// in.Signals() reads 1, then 2 — always
```

**2. When several components feed one port, they are drained in component-name order.**

```go
// alpha, bravo and charlie all pipe into sink's "in" port.
// sink reads alpha's signals, then bravo's, then charlie's —
// whatever order you called AddComponents or PipeTo in.
```

**3. The ports of one component are traversed in port-name order.**

```go
component.WithInputs("i1", "i2", "i3")
// this.Inputs().Signals() reads i1's signals, then i2's, then i3's.
// The same holds for ForEach, Flush and every other traversal.
```

So port names decide the order when a component reads all inputs at once, or writes to several
outputs that meet downstream. Pick names whose alphabetical order is the order you want, for
example `a_header`, `b_body`, `c_footer`.

What is **not** ordered: components in one cycle run concurrently, so the order of their
activation functions is unspecified. Determinism comes from how signals are collected and
delivered. An activation function that uses shared mutable state outside its ports loses the
guarantee.

## Livelock detection

A mesh can activate components forever without progress. For example, two components wait for
each other, or a join has an input port that was never wired. Nothing fails; the same cycle just
repeats. F-Mesh detects this, stops the run and names what is stuck:

```
livelock detected: no progress for 2 consecutive cycles, stopped at cycle #2. Every component
that activated is waiting for inputs and no signals moved, so every following cycle would be
identical to this one
  "joiner" is waiting (keeping inputs): empty input ports [b], holding signals on [a]
  1 other component(s) never activated: no signals ever reached them
```

Here `empty input ports [b]` is the answer: nothing was piped to `b`.

A cycle is **stalled** when both are true:

- every component that activated was waiting for inputs, and
- the number of signals on input ports did not change.

A component that collects input over many cycles is never flagged, because its signal count keeps
changing.

```go
fmesh.New("mesh", fmesh.WithLivelockThreshold(5))   // stop after 5 stalled cycles (default 2)
fmesh.New("mesh", fmesh.WithoutLivelockDetection()) // never stop for this reason
```

Check for it with `errors.Is(err, fmesh.ErrLivelockDetected)`.

Only `ErrWaitKeepingInputs` can cause a livelock. `ErrWaitDroppingInputs` clears the inputs, so
the component has nothing to activate on next cycle, and the mesh stops naturally.

## Error handling strategies

`WithErrorHandlingStrategy` sets how the mesh reacts to component errors and panics:

| Strategy | Behavior |
|----------|----------|
| `StopOnFirstErrorOrPanic` (default) | Stop on the first error or panic |
| `StopOnFirstPanic` | Continue on errors; stop on a panic |
| `IgnoreAll` | Continue on errors and panics |

```go
fm, err := fmesh.New("durable",
    fmesh.WithErrorHandlingStrategy(fmesh.IgnoreAll),
)
```

- When the strategy stops the mesh, `Run` returns an error that names the failing components.
- When the mesh continues, `Run` does not return the error. Find it in the cycle history (see
  [Inspecting a run](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run)). Signals that
  the failed component put on its outputs are still forwarded.

For waiting for inputs (syncing parallel chains), see
[Component — Waiting for inputs](https://github.com/hovsep/fmesh/wiki/301.-Component#waiting-for-inputs).
