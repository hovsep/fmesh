The error from `Run(ctx)` says *why* the mesh stopped. The **run-time report** says *what
happened*: how many cycles ran, which components activated in each cycle, and the outcome.

---

## RuntimeInfo

`Run(ctx)` returns `(*RuntimeInfo, error)`. The report is filled in even when `Run` returns an
error.

| Field / method | Description |
|----------------|-------------|
| `Cycles *cycle.Group` | Ordered history of cycles |
| `StartedAt`, `StoppedAt` | Wall-clock timestamps |
| `Duration()` | Total run time |

```go
ri, err := fm.Run(ctx)
if err != nil {
    log.Printf("mesh stopped: %v (ran %d cycles in %v)", err, ri.Cycles.Len(), ri.Duration())
}

for _, cyc := range ri.Cycles.All() {
    fmt.Printf("Cycle #%d: %d activations, errors=%v\n",
        cyc.Number(),
        cyc.ActivationResults().Len(),
        cyc.HasActivationErrors(),
    )
}
```

What the history holds:

- **`WithCyclesHistoryLimit(n)`** (default: unlimited) keeps only the `n` most recent cycles. Set it for long
  runs — see [Tips & tricks](https://github.com/hovsep/fmesh/wiki/601.-Tips-&-tricks#bounding-memory-on-long-runs).
- **Idle components are not recorded.** A cycle holds results only for components that had input
  in that cycle. If `ByName(name)` returns `nil`, the component did not activate.

## Reading a cycle

Each entry in `RuntimeInfo.Cycles` is a `*cycle.Cycle`:

| Method | Description |
|--------|-------------|
| `Number()` | Sequence number, starting at 1 |
| `ActivationResults()` | Per-component results for this cycle |
| `HasActivationErrors()` / `HasActivationPanics()` | Any errors / panics |
| `HasActivatedComponents()` | At least one component activated |
| `AllActivatedAreWaiting()` | Every activated component is waiting for inputs |
| `AllErrorsCombined()` / `AllPanicsCombined()` | All errors joined, in component-name order |

`RuntimeInfo.Cycles` has the usual group API (`All`, `First`, `Last`, `Find`, `Filter`,
`ForEach`, …) — see [Collections and Groups](https://github.com/hovsep/fmesh/wiki/203.-Collections-and-Groups).

## Activation results

Each activation produces an `*ActivationResult`. Read it with `ComponentName()`, `Activated()`,
`Code()`, `ActivationError()` (all errors joined), `ActivationErrors()` (the list: the function's
error plus any hook errors, or one per attempt with `WithRetry`), `IsError()` and `IsPanic()`. The per-cycle collection has
`ByName`, `All`, `AllOrdered`, `Filter`, `ForEach`, `Every`, `Any`, `Count` and `FindAny`.

| Code | Meaning |
|------|---------|
| `ActivationCodeOK` | Success |
| `ActivationCodeNoInput` | No input signals, so no activation. Never recorded in the history; you only see it from `MaybeActivate` |
| `ActivationCodeReturnedError` | The activation function returned an error |
| `ActivationCodePanicked` | The activation function or a hook panicked. The panic is recovered; the error is a `*component.PanicError` (see [Panics](#panics)) |
| `ActivationCodeWaitingForInputsClear` | Waiting; inputs are cleared |
| `ActivationCodeWaitingForInputsKeep` | Waiting; inputs are kept for the next cycle |
| `ActivationCodeHookFailed` | A component hook returned an error |

`IsError()` is true for `ActivationCodeReturnedError` and `ActivationCodeHookFailed`. `IsPanic()`
is true for `ActivationCodePanicked`.
Helpers: `component.IsWaitingForInput(result)`, `component.WantsToKeepInputs(result)`.

## Errors Run() can return

Match them with `errors.Is`:

| Error | When |
|-------|------|
| `ErrNoComponents` | The mesh has no components. Fails validation before any cycle |
| `ErrReachedMaxAllowedCycles` | The cycle limit was reached (`WithCyclesLimit`; the limit is exact) |
| `ErrTimeLimitExceeded` | The time limit was exceeded (`WithTimeLimit`) |
| `ErrRunCanceled` | The caller's context was canceled or hit its own deadline. Wraps `ctx.Err()`, so `errors.Is(err, context.Canceled)` works |
| `ErrLivelockDetected` | No progress for `WithLivelockThreshold` cycles in a row (default 2). The message names the stuck components and their empty input ports |
| `ErrHitAnErrorOrPanic` | Error or panic under `StopOnFirstErrorOrPanic` |
| `ErrHitAPanic` | Panic under `StopOnFirstPanic` |
| `ErrFailedToDrain` | Moving signals between cycles failed |

A natural stop returns `nil`. An unknown strategy never reaches `Run`: `fmesh.New` rejects it with
`ErrUnsupportedErrorHandlingStrategy`.

## When is a mesh validated?

You never validate by hand:

- `AddComponents` rejects an invalid component at once (for example, one with no activation function).
- Every `Run` first validates the mesh structure (pipe directions, all pipes inside the same mesh).
  A miswired mesh fails fast, with the same error every time.

## Testing a component in isolation

`MaybeActivate(ctx)` runs one activation without a mesh. It is useful in unit tests:

```go
_ = myComponent.InputByName("in").PutPayloads(42)
result := myComponent.MaybeActivate(ctx)
// result.Code() == component.ActivationCodeOK
```

## Panics

A panic in a component never crashes the mesh. It is recovered and becomes the activation error,
a `*component.PanicError`. Its message is one line, so logs stay readable:

```
component parser has activation error: panicked: runtime error: index out of range [3] with length 2
```

The stack trace is kept outside the message. Get it with `errors.As`:

```go
var panicErr *component.PanicError
if errors.As(err, &panicErr) {
    fmt.Printf("%s panicked with %v\n%s\n",
        panicErr.ComponentName, panicErr.Value, panicErr.StackTrace())
}
```

If the panic value is an `error`, `errors.Is` reaches it:

```go
panic(ErrBadInput)          // inside an activation function
...
errors.Is(err, ErrBadInput) // true
```

`fmesh.WithDebug(true)` logs the full stack of every panic, so you rarely need `errors.As` while
debugging.
