## Overview

A hook is a function F-Mesh calls at a fixed point of a run. Use hooks for concerns around your
logic: logging, metrics, tracing, checks, tests. There are three levels:

- **Mesh** — the run and each cycle
- **Component** — each activation
- **Port** — signals and pipes on one port

Every hook takes a `context.Context` first and returns an `error`. Register hooks with
`SetupHooks(func(h *Hooks) { ... })`; on components, the `component.WithHooks(...)` option works
too. Several hooks of one kind run in registration order.

API reference: [FMesh Hooks](https://pkg.go.dev/github.com/hovsep/fmesh#Hooks),
[Component Hooks](https://pkg.go.dev/github.com/hovsep/fmesh/component#Hooks),
[Port Hooks](https://pkg.go.dev/github.com/hovsep/fmesh/port#Hooks).

## F-Mesh Level Hooks

| Hook | When it runs | Argument |
|------|--------------|----------|
| `OnComponentAdded` | `AddComponents` adds a component | `*ComponentAddedContext` (`FMesh`, `Component`) |
| `BeforeRun` | Before the first cycle | `*FMesh` |
| `AfterRun` | When `Run` returns, also after an error | `*FMesh` |
| `BeforeCycle` | At the start of each cycle | `*CycleContext` (`FMesh`, `Cycle`) |
| `AfterCycle` | After all activations of the cycle | `*CycleContext` |

The mesh has two **default hooks**. Yours run after them:

- a `BeforeRun` hook validates the mesh structure (an empty mesh fails with `fmesh.ErrNoComponents`);
- an `AfterCycle` hook logs the cycle's results when `WithDebug(true)` is on.

```go
fm.SetupHooks(func(h *fmesh.Hooks) {
    h.BeforeRun(func(ctx context.Context, fm *fmesh.FMesh) error {
        fmt.Printf("starting mesh %q\n", fm.Name())
        return nil
    })
    h.BeforeCycle(func(ctx context.Context, cc *fmesh.CycleContext) error {
        fmt.Printf("cycle #%d starts\n", cc.Cycle.Number())
        return nil
    })
    h.AfterCycle(func(ctx context.Context, cc *fmesh.CycleContext) error {
        fmt.Printf("cycle #%d: %d activations\n", cc.Cycle.Number(), cc.Cycle.ActivationResults().Len())
        return nil
    })
    h.AfterRun(func(ctx context.Context, fm *fmesh.FMesh) error {
        fmt.Printf("mesh %q done\n", fm.Name())
        return nil
    })
})
```

## Component Level Hooks

| Hook | When it runs | Argument |
|------|--------------|----------|
| `OnCreation` | At the end of `component.New` (after all options and plugins) | `*Component` |
| `BeforeActivation` | Before the activation function | `*Component` |
| `AfterActivation` | After the activation, once, whatever the outcome | `*ActivationContext` (`Component`, `Result`) |

An activation runs three stages: `BeforeActivation` → activation function → `AfterActivation`.

- **`AfterActivation` always runs, exactly once** — like a `finally` block. It runs after success,
  an error, a panic, waiting, and even when `BeforeActivation` failed.
- **One hook sees every outcome.** Branch on `Result.Code()`, `Result.IsError()` or `Result.IsPanic()`.
- **A failing `BeforeActivation` skips the function.** The component still counts as activated, so
  its inputs are cleared like those of any failed activation and it is not tried again with them.
- **A hook error** sets the result to `ActivationCodeHookFailed`. It counts as an activation error.
- **A hook panic** is recovered like a function panic: the result is `ActivationCodePanicked` with
  a `*component.PanicError`. A later hook error never turns a panic into `ActivationCodeHookFailed`.

```go
c, err := component.New("processor",
    component.WithInputs("in"),
    component.WithOutputs("out"),
    component.WithActivationFunc(process),
    component.WithHooks(func(h *component.Hooks) {
        h.BeforeActivation(func(ctx context.Context, c *component.Component) error {
            c.Logger().Println("activation starts")
            return nil
        })
        h.AfterActivation(func(ctx context.Context, ac *component.ActivationContext) error {
            r := ac.Result
            switch {
            case r.IsError(), r.IsPanic():
                ac.Component.Logger().Printf("failed: %v", r.Err())
            case r.IsWaiting():
                ac.Component.Logger().Println("waiting for inputs")
            default:
                ac.Component.Logger().Printf("done: %v", r.Code())
            }
            return nil
        })
    }),
)
```

### A hook that writes outputs

Put it in `AfterActivation` and run it only on success. Written in `BeforeActivation`, the outputs
would be sent even when the function fails, and would pile up while the component waits.

```go
h.AfterActivation(func(ctx context.Context, ac *component.ActivationContext) error {
    if ac.Result.Code() != component.ActivationCodeOK {
        return nil
    }
    return ac.Component.OutputByName("audit").PutPayloads("processed")
})
```

If the extra step must share the component's own error path, compose it into the activation
function instead (see [Composing activation functions](https://github.com/hovsep/fmesh/wiki/301.-Component#composing-activation-functions)).

## Port Level Hooks

Port hooks are set on each port separately.

| Hook | When it runs | Argument (fields) |
|------|--------------|-------------------|
| `OnSignalsAdded` | Signals are added to the port | `*SignalsAddedContext` (`Port`, `SignalsAdded`) |
| `OnSignalsDelivered` | A flush delivered signals through one pipe. Fires on the **source** port, once per destination | `*SignalsDeliveredContext` (`SourcePort`, `DestinationPort`, `SignalsDelivered`) |
| `OnClear` | The port is cleared | `*ClearContext` (`Port`, `SignalsCleared` count) |
| `OnInboundPipe` | A pipe to this port is created | `*InboundPipeContext` (`DestinationPort`, `SourcePort`) |
| `OnOutboundPipe` | A pipe from this port is created | `*OutboundPipeContext` (`SourcePort`, `DestinationPort`) |

On a component with `WithRetry`, a failed attempt's outputs are reset before the next attempt.
That reset fires `OnClear` on each changed output port, and `OnSignalsAdded` when the port's
earlier signals are put back. See [Retrying on error](https://github.com/hovsep/fmesh/wiki/301.-Component#retrying-on-error).

### Naming both ends of a pipe

`OnSignalsAdded` fires on the destination. It cannot tell who sent the signals, or whether they
came through a pipe or a direct `PutSignals`. `OnSignalsDelivered` names both ends, so it can count
traffic per pipe:

- It fires only from `Flush`, once per pipe, **after** the destination accepted the signals.
- `port.ForwardSignals`, `ForwardWithFilter` and `ForwardWithMap` do not fire it. They are not pipes.
- With fan-out, every destination gets the same `*signal.Signal` pointers.

```go
c.InputByName("data").SetupHooks(func(h *port.Hooks) {
    h.OnSignalsAdded(func(ctx context.Context, sa *port.SignalsAddedContext) error {
        for _, sig := range sa.SignalsAdded {
            fmt.Printf("%s.%s got %v\n", sa.Port.ParentComponent().Name(), sa.Port.Name(), sig.Payload())
        }
        return nil
    })
    h.OnClear(func(ctx context.Context, cl *port.ClearContext) error {
        fmt.Printf("%s cleared %d signals\n", cl.Port.Name(), cl.SignalsCleared)
        return nil
    })
})

c.OutputByName("result").SetupHooks(func(h *port.Hooks) {
    h.OnOutboundPipe(func(ctx context.Context, op *port.OutboundPipeContext) error {
        fmt.Printf("pipe %s -> %s\n", op.SourcePort.Name(), op.DestinationPort.Name())
        return nil
    })
    h.OnSignalsDelivered(func(ctx context.Context, d *port.SignalsDeliveredContext) error {
        fmt.Printf("%s -> %s carried %d signals\n",
            d.SourcePort.Name(), d.DestinationPort.Name(), len(d.SignalsDelivered))
        return nil
    })
})
```

## Which context a hook receives

| Fired from | Context |
|------------|---------|
| Anything inside `Run` (cycles, activations, drain) | The run context, with the time-limit deadline |
| `Run` clearing the previous run's outputs (`OnClear`), and `AfterRun` | The caller's context |
| `component.New`, `AddComponents`, `PipeTo` | `context.Background()` |
| `PutSignals` / `PutPayloads` called directly | `context.Background()` |

So `OnSignalsAdded` sees the run context when signals come through a pipe, and
`context.Background()` when you put them by hand.

---

## Hook Execution Order

1. `OnClear` on output ports (clearing the previous run)
2. `BeforeRun`
3. For each cycle:
   - `BeforeCycle`
   - For each component with input, concurrently: `BeforeActivation` → function → `AfterActivation`
   - `AfterCycle`
   - The mesh checks whether to stop
   - Drain: `OnClear` on the inputs of activated components; then, per pipe, `OnSignalsAdded` on
     the destination and `OnSignalsDelivered` on the source; then `OnClear` on the source
4. `AfterRun`

## Error Handling in Hooks

Hooks that run **before** something can stop it, so they are **fail-fast**: the first error skips
the other hooks of the same kind. These are `BeforeRun`, `BeforeCycle`, `BeforeActivation`,
`OnCreation`, `OnSignalsAdded` and the pipe hooks. Every other hook observes something that has
already happened: all hooks of that kind run, and their errors are joined. `AfterRun`,
`AfterCycle` and `AfterActivation` run even when their `Before` hook failed.

| Failing hook | Effect |
|--------------|--------|
| `OnCreation` | `component.New` fails and returns no component |
| `OnComponentAdded` | `AddComponents` fails. All components stay added, and the hooks still run for every one of them |
| `BeforeRun` | `Run` returns the error; no cycle runs |
| `AfterRun` | `Run` returns the error, joined to the run's own error if it has one |
| `BeforeCycle` / `AfterCycle` | The run stops with the error. A failing `BeforeCycle` skips the cycle's activations; `AfterCycle` still runs |
| `BeforeActivation` / `AfterActivation` | The result becomes `ActivationCodeHookFailed`. Under `StopOnFirstErrorOrPanic` the mesh stops and `Run` returns the error |
| `OnSignalsAdded` | The put is undone: the port goes back to its previous signals |
| `OnSignalsDelivered` | The flush fails, but the delivery is not undone. The source port is not cleared |
| `OnClear` | The clear is not undone, but the caller gets the error. In the drain, the run stops with `fmesh.ErrFailedToDrain`; while `Run` clears the previous run's outputs, `Run` returns the error before `BeforeRun` and with no `RuntimeInfo` |
| `OnOutboundPipe` / `OnInboundPipe` | `PipeTo` fails and that pipe is removed. Pipes made earlier in the same call stay |

A hook that panics is recovered only where the panic would otherwise kill the process: on an
activation goroutine. That covers the component hooks and port hooks fired while a component
activates (its own `PutSignals`, the reset between retries); the panic becomes an
`ActivationCodePanicked` result. Mesh hooks, and port hooks fired by the drain or by your own
calls, run on the goroutine that called `Run` (or `New`, `AddComponents`, `PipeTo`,
`PutSignals`), so their panic reaches that caller. `AfterRun` still runs first.

```go
fm.SetupHooks(func(h *fmesh.Hooks) {
    h.BeforeCycle(func(ctx context.Context, cc *fmesh.CycleContext) error {
        if cc.Cycle.Number() > 100 {
            return errors.New("runaway mesh")
        }
        return nil
    })
})
```

## Best Practices

- **Keep hooks cheap.** They run inside the run loop. A slow `AfterCycle` slows every cycle. Port
  hooks fire on every put and clear, including the drain. Send slow work to a buffered channel
  read by your own goroutine.
- **Observe, don't steer.** Change signals in activation functions, not in hooks. A hook that
  clears or adds signals fights the scheduler.
- **Guard shared state.** Component and port hooks fire from concurrent activation goroutines.
- **Mind the order.** Hooks of one kind run in registration order, and a failing `Before` hook
  skips the ones after it.

Use the **activation function** for business logic and signal processing. Use **hooks** for
logging, metrics, tracing, validation and tests.

## Example: timing a component

One component never activates twice at the same time, so this needs no lock. Hooks on several
components that write one shared value need a mutex.

```go
var (
    start time.Time
    total time.Duration
)

c.SetupHooks(func(h *component.Hooks) {
    h.BeforeActivation(func(ctx context.Context, c *component.Component) error {
        start = time.Now()
        return nil
    })
    h.AfterActivation(func(ctx context.Context, ac *component.ActivationContext) error {
        total += time.Since(start)
        return nil
    })
})
```

The run's total time is already in `RuntimeInfo.Duration()` — see
[Inspecting a run](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run).

To package hooks so they attach to any component or mesh — including the `OnComponentAdded`
pattern that instruments every component — see [502. Plugins](https://github.com/hovsep/fmesh/wiki/502.-Plugins).
