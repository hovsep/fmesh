## Overview

A plugin is a named bundle of setup code. You pass it to a constructor, and its `Init` runs once.
Whatever `Init` sets up — hooks, ports, metadata, pipes — becomes part of the object.

The value of a plugin: you write a concern once and attach it to any component or mesh, without
editing either.

| Level | Interface | Attach with | `Init` receives | Query |
|-------|-----------|-------------|-----------------|-------|
| Component | `component.Plugin` | `component.WithPlugins(...)` | `*component.Component` | `c.HasPlugin(name)` |
| Mesh | `fmesh.Plugin` | `fmesh.WithPlugins(...)` | `*fmesh.FMesh` | `fm.HasPlugin(name)` |

Both interfaces have two methods:

```go
Name() string
Init(T) error
```

Rules for both levels:

- **Names are unique.** Two plugins with one name is a construction error.
- **A failing `Init` fails construction.** `New` returns `nil` and the error.
- **`Init` runs in name order.** Plugins usually register hooks, and hooks run in registration
  order. Sorting keeps that order the same on every run.

## Component plugins

`Init` runs inside `component.New`, after all other options. The component is complete, so a
plugin can add ports, metadata, state and hooks:

```go
type PricePlugin struct{}

func (PricePlugin) Name() string { return "price" }

func (PricePlugin) Init(c *component.Component) error {
    // Add ports
    if err := c.AddInputs("price_in"); err != nil {
        return err
    }
    if err := c.AddOutputs("price_out"); err != nil {
        return err
    }

    // Add behavior
    c.SetupHooks(func(h *component.Hooks) {
        h.OnCreation(func(ctx context.Context, this *component.Component) error {
            this.State().Set("base_price", 77.5)
            return nil
        })
        // Emit only after the component's own function succeeded.
        h.AfterActivation(func(ctx context.Context, ac *component.ActivationContext) error {
            if ac.Result.Code() != component.ActivationCodeOK {
                return nil
            }
            return ac.Component.OutputByName("price_out").PutPayloads(999.0)
        })
    })

    // Add metadata
    c.Meta().Set("plugin/price/version", "v1.2.4")
    return nil
}
```

```go
c, err := component.New("priced",
    component.WithInputs("i1"),
    component.WithOutputs("o1"),
    component.WithActivationFunc(myLogic),
    component.WithPlugins(PricePlugin{}),
)
```

Order inside `component.New`: **options → plugin `Init`s → `OnCreation` hooks.** So an
`OnCreation` hook registered by a plugin still runs.

Why `AfterActivation` with a success check: see
[Hooks — A hook that writes outputs](https://github.com/hovsep/fmesh/wiki/501.-Hooks#a-hook-that-writes-outputs).

## Mesh plugins

A mesh plugin is the place for concerns that span the whole mesh: measuring, tracing, asserting,
wiring. `Init` runs inside `fmesh.New`, after the options.

### You cannot walk components in `Init`

A mesh starts **empty**. `AddComponents` fills it later, so at `Init` time there is nothing to walk:

```go
func (p *MyPlugin) Init(fm *fmesh.FMesh) error {
    fm.Components().ForEach(...) // always empty here
    return nil
}
```

Instead, register an `OnComponentAdded` hook and instrument each component **when it arrives**:

```go
type ActivationCounter struct {
    count atomic.Int64
}

func (p *ActivationCounter) Name() string { return "activation-counter" }

func (p *ActivationCounter) Init(fm *fmesh.FMesh) error {
    fm.SetupHooks(func(h *fmesh.Hooks) {
        h.OnComponentAdded(func(ctx context.Context, added *fmesh.ComponentAddedContext) error {
            added.Component.SetupHooks(func(ch *component.Hooks) {
                ch.AfterActivation(func(ctx context.Context, ac *component.ActivationContext) error {
                    p.count.Add(1)
                    return nil
                })
            })
            return nil
        })
    })
    return nil
}

func (p *ActivationCounter) Count() int64 { return p.count.Load() }
```

```go
counter := &ActivationCounter{}
fm, err := fmesh.New("mesh", fmesh.WithPlugins(counter))
// ... AddComponents, Run ...
fmt.Println(counter.Count())
```

The plugin sees every activation in the mesh, and no component knows about it.

Two consequences:

- **A component is looked at only when it is added.** Ports added later with
  `AddInputs`/`AddOutputs` are invisible to the plugin. Declare ports in `component.New`.
- **Component hooks run concurrently.** Guard shared state. When timing, read the clock
  *outside* your lock, or each component is charged for the others' lock contention.

## Bundled plugins

F-Mesh ships two mesh plugins, each in its own package with its own README:

```go
import (
    "github.com/hovsep/fmesh/plugin/autowire"
    "github.com/hovsep/fmesh/plugin/profiler"
)

fm, err := fmesh.New("mesh", fmesh.WithPlugins(
    profiler.New(),
    autowire.Broadcast("time"),
))
```

A plugin adds behavior to a run through hooks. Exporters only read a mesh, so they are plain
values, not plugins: see [701. Export](https://github.com/hovsep/fmesh/wiki/701.-Export).

### profiler at a glance

`profiler.Plugin` times whole runs, single cycles, and each component's activations. The
per-component numbers are its main value: a Go CPU profile of a mesh is mostly scheduler work and
barely separates one component from another.

- Timing is on by default. Opt-in modes add per-pipe throughput and a per-cycle timeline.
- Every number belongs to the mesh; nothing process-wide is measured.
- Each activation goroutine gets `runtime/pprof` labels `fmesh.mesh` and `fmesh.component`, so you
  can focus a CPU profile on one component.

```go
prof := profiler.New() // timing only; profiler.New(profiler.ModeAll) measures everything

fm, err := fmesh.New("mesh", fmesh.WithPlugins(prof))
// ... AddComponents, Run ...

fmt.Println(prof.Report())
```

| Call | Returns |
|------|---------|
| `profiler.New(modes...)` | The plugin. Modes: `ModeTiming` (default), `ModeThroughput`, `ModeTimeline`, `ModeAll` |
| `Report()` | A printable summary of everything measured |
| `Runs()`, `Cycles()` | A `Stat` (`Count`, `Total`, `Min`, `Max`, `Avg()`) for whole runs / single cycles |
| `Components()`, `TopN(n)` | Per-component stats; `TopN` sorts by activation count |
| `Pipes()`, `TopNPipes(n)` | Per-pipe signal flow (`ModeThroughput`) |
| `Timeline()` | One `CycleRecord` per cycle (`ModeTimeline`); bound it with `SetTimelineLimit(n)` |
| `Reset()` | Clears every measurement |

Modes, costs, accessors and the timeline are in the
[package README](https://github.com/hovsep/fmesh/blob/main/plugin/profiler/README.md) and
[godoc](https://pkg.go.dev/github.com/hovsep/fmesh/plugin/profiler).

### autowire — pipes by naming convention

Large meshes have a lot of obvious wiring: everything that keeps time gets the clock. Writing it
by hand is a list to maintain, and a forgotten pipe fails silently — the component just waits for
input that never comes.

`autowire.Plugin` derives the pipes from a rule. The rule maps an output port to the name of the
input port that should receive it:

```go
fm, err := fmesh.New("mesh",
    fmesh.WithPlugins(autowire.Broadcast("time")),
)

// No PipeTo calls: every input named "time" is wired to every output named "time".
err = fm.AddComponents(clock, heart, lung)
```

| Constructor | Rule |
|-------------|------|
| `autowire.Broadcast("time")` | every output named `time` → every input named `time` |
| `autowire.BroadcastAs("tick", "time")` | every output named `tick` → every input named `time` |
| `autowire.Prefixed("env_")` | an output → the input named `<prefix><component>_<port>`, e.g. `env_sun_uvi` |
| `&autowire.Plugin{InputNameFor: func(source *component.Component, output *port.Port) string {...}}` | your own rule; return `""` to skip |

- Wiring works **in both directions** on every arrival: a new component's inputs get the existing
  outputs, and its outputs reach the existing inputs. So the order of `AddComponents` does not matter.
- One rule per plugin. For several rules, add several plugins. Each has its own name, so they
  coexist, and a pair matched by two rules is wired once.
- A component is never wired to **itself**. For a loopback, use `c.LoopbackPipe(out, in)`.
- Ports must exist **before** `AddComponents`.

```go
fm, err := fmesh.New("habitat", fmesh.WithPlugins(
    autowire.BroadcastAs("tick", "time"),
    autowire.Prefixed("env_"),
))
```

## Choosing a level

| You want to... | Use |
|----------------|-----|
| Give one kind of component extra ports, state or behavior | Component plugin |
| Observe or wire *every* component without touching any | Mesh plugin + `OnComponentAdded` |
| React to an event in one mesh, once | A plain hook — see [501. Hooks](https://github.com/hovsep/fmesh/wiki/501.-Hooks) |

A plugin pays off when the setup is reusable. For a one-off, call `SetupHooks` directly.
