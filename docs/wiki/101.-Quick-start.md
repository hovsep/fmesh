Let's build a first mesh. It computes the **min**, **max** and **sum** of a list of numbers. The
three calculations run **concurrently**, and a reporter combines their results.

This small mesh already shows three things F-Mesh does for you:

- **fan-out**: one output feeds many components;
- **concurrency without goroutines**: ready components run at the same time;
- **fan-in with automatic sync**: the reporter runs once all results are in.

The topology:

```
                     these 3 run concurrently
                     ┌──> [min] ──┐
[source] ──fan-out───┼──> [max] ──┼── fan-in ──> [report]
                     └──> [sum] ──┘
```

### Creating a mesh

A mesh has a name:

```go
fm, err := fmesh.New("stats")
if err != nil {
    // handle error
}
```

`New` also takes options such as `fmesh.WithCyclesLimit`, `fmesh.WithTimeLimit` and
`fmesh.WithErrorHandlingStrategy`. The defaults are fine here.

### Creating a component

A component does its work in an **activation function**. This helper builds a worker that reads
every number on its input port and reduces them to one result:

```go
worker := func(name string, reduce func([]int) int) *component.Component {
    c, _ := component.New(name,
        component.WithInputs("in"),
        component.WithOutputs("out"),
        component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
            var nums []int
            for _, s := range this.InputByName("in").Signals().All() {
                n, err := s.As[int]() // a non-int payload is an error, not a panic
                if err != nil {
                    return err
                }
                nums = append(nums, n)
            }
            return this.OutputByName("out").PutSignals(signal.New(reduce(nums)))
        }),
    )
    return c
}

minC := worker("min", slices.Min[[]int])
maxC := worker("max", slices.Max[[]int])
sumC := worker("sum", func(nums []int) int {
    total := 0
    for _, n := range nums {
        total += n
    }
    return total
})
```

The activation function **reads inputs, writes outputs and returns**. Some things to note:

- When a component activates, its input signals are already on its ports. You just get them; you
  never wait for them.
- Writing is non-blocking. You _put_ signals on a port; you do not _send_ them.
- So time is discrete: an activation function does no async I/O with other components.

### The source

A **source** component forwards whatever arrives to its output:

```go
source, _ := component.New("source",
    component.WithInputs("in"),
    component.WithOutputs("out"),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        return port.ForwardSignals(ctx, this.InputByName("in"), this.OutputByName("out"))
    }),
)
```

The **pipes** do the broadcasting (wired below), not the component. In a real mesh the source
often reads a file or a database, and all consumers share that work.

### The reporter

The **reporter** has one input port per worker and combines the results:

```go
report, _ := component.New("report",
    component.WithInputs("min", "max", "sum"),
    component.WithOutputs("out"),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        summary := fmt.Sprintf("min=%v  max=%v  sum=%v",
            this.InputByName("min").Signals().FirstPayloadOrNil(),
            this.InputByName("max").Signals().FirstPayloadOrNil(),
            this.InputByName("sum").Signals().FirstPayloadOrNil(),
        )
        return this.OutputByName("out").PutSignals(signal.New(summary))
    }),
)
```

`min`, `max` and `sum` sit at the same depth in the graph. So their results reach the reporter
**in the same cycle**, and it activates once with all three. For paths of different length, wait
explicitly: see [Waiting for inputs](https://github.com/hovsep/fmesh/wiki/301.-Component#waiting-for-inputs).

### Adding components to the mesh

```go
if err := fm.AddComponents(source, minC, maxC, sumC, report); err != nil {
    // handle error
}
```

>[!IMPORTANT]
Every component must be added to the mesh. `AddComponents` returns an error for an invalid component or a duplicate name.

### Connecting components with pipes

A pipe goes from an output port to one or more input ports. One `PipeTo` call with several
destinations is a **fan-out**:

```go
// Fan-out: source broadcasts to all three workers
if err := source.OutputByName("out").PipeTo(
    minC.InputByName("in"),
    maxC.InputByName("in"),
    sumC.InputByName("in"),
); err != nil {
    // handle error
}

// Fan-in: each worker reports to its own port on the reporter
_ = minC.OutputByName("out").PipeTo(report.InputByName("min"))
_ = maxC.OutputByName("out").PipeTo(report.InputByName("max"))
_ = sumC.OutputByName("out").PipeTo(report.InputByName("sum"))
```

This wiring *is* the program. To add a median, you add one component and two pipes. No existing
code changes.

### Passing initial signals

Put the numbers on the source's input. `PutPayloads` makes one signal per value:

```go
if err := source.InputByName("in").PutPayloads(4, 8, 15, 16, 23, 42); err != nil {
    // handle error
}
```

There is no special start API. You put signals on the inputs of your entry component. Putting
signals triggers nothing by itself; it is like appending to a slice.

### Running the mesh

```go
if _, err := fm.Run(ctx); err != nil {
    fmt.Println("mesh failed:", err)
}
```

`Run` activates components in waves (cycles) until the mesh stops. It stops on an error, a panic,
a limit, or naturally. The natural stop is the normal case: no component has signals on any input
port. See [401. Scheduling rules](https://github.com/hovsep/fmesh/wiki/401.-Scheduling-rules).

>[!NOTE]
`Run` blocks until the mesh stops. Check the returned error to see why it stopped.

### Getting the results

Read the summary from the reporter's output port:

```go
result := fm.ComponentByName("report").OutputByName("out").Signals().FirstPayloadOrDefault("")
fmt.Println("Result:", result)
```

Output:

`Result: min=4  max=42  sum=108`

You have built your first F-Mesh.

### Why not just functions and goroutines?

For a one-off calculation, a plain function is fine. But to run three calculations concurrently
and combine their results, plain Go needs three goroutines, a `sync.WaitGroup` or channels, and
manual result collection.

Here you wrote none of that:

- `min`, `max` and `sum` run in parallel because they are ready in the same cycle;
- ports buffer the data;
- the reporter fires once all three results arrive.

As the graph grows (more stages, fan-out, feedback loops), this free concurrency and sync matters
more. You describe **how data flows**; the framework runs it.

### Error handling

Methods that can fail return `error` last: `fmesh.New`, `component.New`, `AddComponents`,
`PutSignals`, `PutPayloads`, `PipeTo`, `Run`. Check each one in real code.

Lookups like `ComponentByName` and `InputByName` return `nil` when the name does not exist: see [Port lookups return nil](https://github.com/hovsep/fmesh/wiki/603.-Caveats#port-lookups-return-nil).
