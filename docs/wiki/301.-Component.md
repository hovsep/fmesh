## Overview

A component is the main building block of a mesh. Its behavior is one function: the **activation function**.

- A component is not a long-running goroutine. F-Mesh calls its activation function when the component has input signals, and the function returns.
- Keep activation functions small and fast: read inputs, compute, write outputs. A function that never returns blocks the whole mesh.
- A component can keep **state** between activations. No locks are needed: a component activates at most once per cycle, in one goroutine.

Full API: [component package](https://pkg.go.dev/github.com/hovsep/fmesh/component).

## Key elements of a component

| Element | Description |
|---|---|
| **Name** | Unique within one mesh. Used for lookup and debugging. |
| **Description** | Optional (`WithDescription`). Useful for export and visualization. |
| **Inputs / Outputs** | Any number of ports. An activation does not have to use all of them. |
| **Activation function** | The logic. Runs when the component is scheduled. |
| **State** | A key-value store that persists between activations. |
| **Metadata** | String and numeric entries for filtering and cross-cutting concerns. See [Metadata](https://github.com/hovsep/fmesh/wiki/202.-Metadata). |
| **Logger** | A standard `*log.Logger`, prefixed with the component name. |

## Activation function

Every activation function has the same signature:

```go
func(ctx context.Context, this *component.Component) error
```

Through `this` you reach `Inputs()`, `Outputs()`, `InputByName()`, `OutputByName()`, `State()` and `Logger()`. Inputs and outputs are both a `*port.Collection` (see [Collections and Groups](https://github.com/hovsep/fmesh/wiki/203.-Collections-and-Groups)).

A typical function reads input signals, computes, optionally uses state, and writes output signals. Written this way, it behaves like a pure function.

**Example: sum all signals on one port**

```go
func(ctx context.Context, this *component.Component) error {
    sum := 0
    for _, sig := range this.InputByName("i1").Signals().All() {
        n, err := sig.As[int]()
        if err != nil {
            return err
        }
        sum += n
    }
    return this.OutputByName("o1").PutSignals(signal.New(sum))
}
```

`sig.As[int]()` returns an error for a payload of another type, instead of panicking like a bare type assertion. See [Reading typed payloads](https://github.com/hovsep/fmesh/wiki/201.-Signals#reading-typed-payloads).

## Composing activation functions

A component has one activation function. That function often does several steps in a fixed order. The `component` package has combinators that build one `ActivationFunc` from several:

```go
component.WithActivationFunc(component.Sequential(
    component.RequireInputs("config", "data"),
    readControls,
    advanceState,
    publishResult,
))
```

`Sequential` runs the functions in order and stops at the first error. That error is the component's own error. So a step that returns `component.ErrWaitKeepingInputs` suspends the component, exactly as one big function would.

### When vs RequireInputs

Both check inputs. They behave differently:

| Combinator | Behavior | Use when |
|---|---|---|
| `component.When(pred, fn)` | Skips `fn` and returns `nil`. The component does nothing this cycle, and its inputs are cleared. | The component is **idle** until something arrives. |
| `component.RequireInputs(names...)` | Returns `ErrWaitKeepingInputs`. The component waits and **keeps** what already arrived. | The component **needs** every named input to compute. |

```go
// Idle: nothing on "trigger" means nothing to do
component.When(component.HasSignalsOn("trigger"), doWork)

// Needs both: keep the one that arrived and wait for the other
component.Sequential(component.RequireInputs("left", "right"), sum)
```

> [!WARNING]
> Using `When` where you need `RequireInputs` silently drops signals: the cycle ends normally and the partial inputs are cleared.

Unknown port names:

- `HasSignalsOn` returns `false` for a name the component has no port for.
- `RequireInputs` **fails** the activation (`required input port "..." does not exist`). Waiting on a port that does not exist would wait forever.

### Pipeline

`Pipeline` covers a common shape: read inputs, transform the group, write one output.

```go
component.WithActivationFunc(component.Pipeline(
    []string{"in"}, // input ports, read in this order
    "out",          // one output port
    dropEmpty,      // stages, applied in order
    normalize,
))
```

A stage is a `component.PipelineStage`:

```go
func(signals *signal.Group) (*signal.Group, error)
```

- Inputs are read in the order the names are given.
- A failing stage is named in the error (`pipeline stage 1 failed: ...`).
- A stage that drops everything must return an **empty** group. Returning `nil` is an error.
- An unknown input or output port name fails the activation and names the port.

Combinators compose a component's own behavior. Code **outside** the component (for example a plugin) uses `BeforeActivation` / `AfterActivation` hooks instead. See [Hooks](https://github.com/hovsep/fmesh/wiki/501.-Hooks).

## Stateful component

Components are stateless by default. Use `State()` to keep data between activations. Set initial keys with `WithInitialState`.

**Example: a counter that passes signals through**

```go
counter, err := component.New("stateful_counter",
    component.WithDescription("counts all observed signals and passes them downstream"),
    component.WithInputs("in"),
    component.WithOutputs("out"),
    component.WithInitialState(func(state component.State) {
        state.Set("count", 0)
    }),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        count, err := this.State().GetTyped[int]("count")
        if err != nil {
            return err
        }
        count += this.InputByName("in").Signals().Len()
        this.State().Set("count", count)
        this.Logger().Println("signals observed so far:", count)

        return port.ForwardSignals(ctx, this.InputByName("in"), this.OutputByName("out"))
    }),
)
```

### State API

`component.State` is a `map[string]any` with helper methods. See the [State type](https://pkg.go.dev/github.com/hovsep/fmesh/component#State).

| Method | Description |
|--------|-------------|
| `Has(key)` | True if the key exists |
| `Get(key)` | Value, or `nil` |
| `GetOrDefault(key, default)` | Value, or the default |
| `GetTyped[T](key)` | Value as `T`; an error if the key is missing or has another type |
| `Set(key, value)` | Sets a value |
| `SetIfAbsent(key, value)` | Sets only if the key is missing; returns whether it set |
| `Delete(key)` | Removes a key |
| `Upsert(key, fn)` | Stores `fn(current)`; `current` is `nil` if missing |
| `Update(key, fn)` | Like `Upsert`, but only if the key exists; returns whether it did |
| `UpdateAndGet(key, fn)` | Like `Upsert`, and returns the stored value |

`ResetState()` wipes the state.

### Indexed ports

Create many ports with a prefix and an index range:

```go
c, err := component.New("worker",
    component.WithIndexedInputs("in", 0, 3), // in0, in1, in2, in3
    component.WithIndexedOutputs("out", 0, 3),
    component.WithActivationFunc(myFunc),
)
```

After construction, use `AddIndexedInputs(prefix, start, end)` / `AddIndexedOutputs`. A start greater than the end returns `port.ErrInvalidRangeForIndexedGroup`.

### LoopbackPipe

Pipe a component's output to its own input by port names:

```go
err := c.LoopbackPipe("o1", "i1") // same as c.OutputByName("o1").PipeTo(c.InputByName("i1"))
```

Unlike the long form, it returns an error that names a missing port.

## Nested meshes

There is no special "sub-mesh" type. A component can **run another mesh inside its activation function** and treat it as a black box. Do not add the inner mesh's components to the outer mesh. Build the inner mesh separately and call its `Run`.

```go
factorizer, err := component.New("factorizer",
    component.WithInputs("in"),
    component.WithOutputs("out"),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        inner := buildFactorizationMesh() // your inner *fmesh.FMesh

        return this.InputByName("in").Signals().ForEach(func(sig *signal.Signal) error {
            num, err := sig.As[int]()
            if err != nil {
                return err
            }

            // Outer signal -> inner mesh input
            if err := inner.ComponentByName("starter").InputByName("in").PutSignals(sig); err != nil {
                return err
            }

            if _, err := inner.Run(ctx); err != nil {
                return fmt.Errorf("inner mesh failed: %w", err)
            }

            // Inner mesh output -> outer signal
            factors := inner.ComponentByName("results").OutputByName("factors").Signals().AllPayloads()
            return this.OutputByName("out").PutSignals(signal.New(myResult{Num: num, Factors: factors}))
        })
    }),
)
```

- **Blocking**: `inner.Run(ctx)` blocks until the inner mesh stops.
- **Separate**: the outer scheduler does not see inner components. Pipes work only inside one mesh.
- **Manual bridging**: you copy signals in and out yourself.
- **Recursive**: an inner component can wrap another mesh, to any depth.
- **Reuse**: you can build the inner mesh once and run it many times. One `Run` must finish before the next starts.

## Returning errors

Return `nil` on success. Return an error to report a problem.

- **Default strategy** (`StopOnFirstErrorOrPanic`): the first error stops the mesh, and `Run` returns an error.
- **Tolerant strategies** (`StopOnFirstPanic`, `IgnoreAll`): the mesh keeps running. Signals the component put on its outputs before the error are still sent downstream.
- See [Error handling strategies](https://github.com/hovsep/fmesh/wiki/401.-Scheduling-rules#error-handling-strategies).
- An `AfterActivation` hook sees each result as it happens (`Result.IsError()`, `Result.IsPanic()`). To inspect results after the run, see [Inspecting a run](https://github.com/hovsep/fmesh/wiki/402.-Inspecting-a-run).

```go
func(ctx context.Context, this *component.Component) error {
    // Written before the error: still sent downstream under a tolerant strategy
    if err := this.OutputByName("log").PutSignals(signal.New("activated")); err != nil {
        return err
    }

    // Error on an empty port (signal.ErrNoSignalsInGroup) or a non-int payload
    n, err := this.InputByName("i1").Signals().FirstAs[int]()
    if err != nil {
        return fmt.Errorf("reading i1: %w", err)
    }

    return this.OutputByName("o1").PutSignals(signal.New(n * 2))
}
```

Write error messages that help to find the cause.

## Waiting for inputs

Sometimes a component must not run until signals are on several ports. Return a sentinel error from the activation function to make it wait.

Look at this mesh:

<img src="https://github.com/user-attachments/assets/41bfa02d-3d46-4fc4-b8b6-606f7a940c76" width="700">

We start both chains in the same cycle:

```go
_ = fm.ComponentByName("d1").InputByName("i1").PutSignals(signal.New(1))
_ = fm.ComponentByName("d4").InputByName("i1").PutSignals(signal.New(2))
```

Execution runs in waves:

1. **d4**, **d1**
2. **d5**, **d2**
3. **sum**, **d3**
4. **sum**

**The problem:** `sum` needs one signal from each chain. The left chain is shorter, so its signal reaches `sum` in cycle 3, one cycle before the other.

**The fix:** make `sum` wait until both ports have signals.

```go
s, err := component.New("sum",
    component.WithInputs("i1", "i2"),
    component.WithOutputs("o1"),
    component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
        if !this.Inputs().ByNames("i1", "i2").AllHaveSignals() {
            return component.ErrWaitKeepingInputs
        }

        a := this.InputByName("i1").Signals().FirstPayloadOrDefault(0)
        b := this.InputByName("i2").Signals().FirstPayloadOrDefault(0)
        return this.OutputByName("o1").PutSignals(signal.New(a + b))
    }),
)
```

Two sentinel errors control waiting:

| Error | Behavior | Use when |
|-------|----------|----------|
| `component.ErrWaitKeepingInputs` | Wait and **keep** the input signals for the next cycle | Every signal matters, for example a join waiting for its second operand |
| `component.ErrWaitDroppingInputs` | Wait and **drop** the signals received this cycle | A partial input is useless without the rest |

- Choose the mode on purpose. The wrong one loses data or stalls silently.
- `errors.Is(err, component.ErrWaitingForInputs)` matches both modes.
- A waiting component's outputs are not sent downstream in that cycle.
- Only `ErrWaitKeepingInputs` can stall a mesh forever. [Livelock detection](https://github.com/hovsep/fmesh/wiki/401.-Scheduling-rules#livelock-detection) stops such a run.

The same check is available as a combinator. It also fails on a port name that does not exist:

```go
component.WithActivationFunc(component.Sequential(
    component.RequireInputs("i1", "i2"),
    sum, // runs only when both ports have signals
))
```

See [Composing activation functions](#composing-activation-functions).

## Component hooks

Hooks add behavior around the activation function without changing it. Use them for logging, metrics, tracing and debugging.

| Hook | Runs |
|---|---|
| `OnCreation` | During `component.New`, after all options and plugins |
| `BeforeActivation` | Before the activation function |
| `AfterActivation` | Once after every activation, whatever the outcome. Check `Result.Code()`, `Result.IsError()`, `Result.IsPanic()` |

```go
c.SetupHooks(func(h *component.Hooks) {
    h.BeforeActivation(func(ctx context.Context, c *component.Component) error {
        c.Logger().Println("starting activation")
        return nil
    })
    h.AfterActivation(func(ctx context.Context, hc *component.ActivationContext) error {
        if hc.Result.IsError() {
            hc.Component.Logger().Println("error:", hc.Result.ActivationError())
            return nil
        }
        hc.Component.Logger().Println("finished:", hc.Result.Code())
        return nil
    })
})
```

- A hook that writes outputs belongs in `AfterActivation`, guarded by `hc.Result.Code() == component.ActivationCodeOK`.
- A hook that returns an error marks the result `ActivationCodeHookFailed` (`IsError()` is true).
- A panic inside a hook is recovered, and the result becomes `ActivationCodePanicked`.

Full details: [Hooks](https://github.com/hovsep/fmesh/wiki/501.-Hooks).
