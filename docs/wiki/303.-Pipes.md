One component is rarely useful. The power of F-Mesh comes from connecting components with **pipes**, so each one solves a small step of a bigger problem.

Pipes are simple:

- No pipe object is stored. `PipeTo` just registers the destination on the source port.
  `port.Pipe` only describes an edge to pass to `MultiPipe`.
- One pipe connects exactly one output port to exactly one input port.
- One-to-many and many-to-one connections are just several pipes.

## One-to-one connections

![](https://github.com/user-attachments/assets/c833488a-5d39-4624-8410-f068c10c8d26)

```go
// Connect output "o1" of c1 to input "i1" of c2
if err := c1.OutputByName("o1").PipeTo(c2.InputByName("i1")); err != nil {
    return err
}
```

All signals put on `o1` of `c1` are moved to `i1` of `c2` when the cycle drains. The output port is cleared after the move.

## One-to-many connections

![](https://github.com/user-attachments/assets/09f18fe8-a3eb-444a-b6e9-08fc7ce658ed)

Pass several destinations to `PipeTo`:

```go
err := c1.OutputByName("o1").PipeTo(
    c2.InputByName("i1"),
    c3.InputByName("i2"),
    c4.InputByName("i3"),
)
```

Every signal on `o1` goes to all three destination ports.

`PipeTo` does not check for an existing pipe: piping the same output to the same input twice makes
two pipes, and every signal arrives twice. See
[Piping twice delivers twice](https://github.com/hovsep/fmesh/wiki/603.-Caveats#piping-twice-delivers-twice).

To inspect the wiring, `out.Pipes()` returns the destination ports (a `*port.Group`), and
`out.HasPipes()` tells whether there is any. An output with no pipes keeps its signals: nothing
moves them.

> [!IMPORTANT]
> Signals are passed **by pointer**, not deep-copied. With fan-out, all destinations share the same `*signal.Signal`.
> * Signals are copy-on-write: `WithMeta`, `MapPayload` and similar methods return a new signal and do not change the shared one.
> * The payload is not copied. Never mutate a payload you received (for example a map or slice). Build a new one instead.

## Many-to-one connections

![](https://github.com/user-attachments/assets/2d367069-f267-4d70-9064-c60162500720)

Pipe several outputs to the same input:

```go
_ = c1.OutputByName("o1").PipeTo(sink.InputByName("i1"))
_ = c2.OutputByName("o1").PipeTo(sink.InputByName("i1"))
_ = c3.OutputByName("o1").PipeTo(sink.InputByName("i1"))
```

All signals from `c1`, `c2` and `c3` appear on `i1` of `sink`, in upstream component-name order.

## Wiring many pipes at once

A bare error from `PipeTo` does not tell you which of many wiring lines failed. `port.MultiPipe` takes a list of edges and names the one that failed:

```go
if err := port.MultiPipe(
    port.Pipe{From: c1.OutputByName("o1"), To: c2.InputByName("i1")},
    port.Pipe{From: c2.OutputByName("o1"), To: c3.InputByName("i1")},
    port.Pipe{From: c3.OutputByName("o1"), To: sink.InputByName("i1")},
); err != nil {
    // e.g. piping o1 -> i1: pipe validation failed: pipe must go from output to input
    return err
}
```

A nil port is an error, not a panic: `cannot pipe: o1 -> <missing port>`. `OutputByName` / `InputByName` return `nil` for an unknown name, so a typo becomes an error that names the edge.

To copy signals right away instead of registering a connection, see [MultiForward](https://github.com/hovsep/fmesh/wiki/302.-Ports#forwarding-several-pairs-at-once).

## Cyclic connections

![](https://github.com/user-attachments/assets/7bec7fc4-12ec-4583-99ec-611d4a7ad88d)

A component can pipe its output to its own input. This is fully supported and common. Like recursion in functional programming, it lets a component activate itself again.

```go
_ = c1.OutputByName("o1").PipeTo(c1.InputByName("i1"))
```

The component activates again in the next cycle if any of its input ports has a signal. So the component itself decides how many cycles to run: it stops by not writing to `o1`.

## LoopbackPipe

`LoopbackPipe` is a shorter form of a cyclic pipe, by port names:

```go
err := c.LoopbackPipe("o1", "i1")
```

It is the same as `c.OutputByName("o1").PipeTo(c.InputByName("i1"))`, but returns an error that names a missing port.

## Conditional forwarding

Inside an activation function you can route signals without pipes, with the port forwarding helpers. They copy signals to the destination and do not clear the source.

```go
// Forward everything
err := port.ForwardSignals(ctx, this.InputByName("in"), this.OutputByName("out"))

// Forward only high-priority signals
err = port.ForwardWithFilter(ctx, this.InputByName("in"), this.OutputByName("high"),
    signal.MetaEquals("priority", "high"))

// Transform payloads while forwarding
err = port.ForwardWithMap(ctx, this.InputByName("in"), this.OutputByName("out"),
    func(s *signal.Signal) *signal.Signal {
        return s.MapPayload(func(p any) any { return strings.ToUpper(p.(string)) })
    })
```

## Patterns

Ports and pipes are enough to build many patterns:

| Pattern | Idea |
|---|---|
| **Fan-out** (broadcast, observer, pub-sub) | Send signals to many components |
| **Fan-in** (merge, aggregator) | Combine signals from many components |
| **Pipeline** | Pass signals through processing stages in order |
| **Load balancer** | Spread signals across several components |
| **Filter** | Pass or block signals by a condition |
| **State machine** | Change state based on incoming signals |
| **Circuit breaker** | Stop processing for a while after too many failures |
| **Rate limiter** | Limit how fast signals flow |
| **Retry** | Process failed signals again |
| **Batching** | Process signals in groups |

See [Patterns and recipes](https://github.com/hovsep/fmesh/wiki/602.-Patterns-and-recipes) for worked examples.
