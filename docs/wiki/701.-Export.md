## Exporting Your Mesh

Export the structure of a mesh as data or as a diagram. Every exporter is a mesh plugin.

| Format | Package | Module | Per-cycle export |
|--------|---------|--------|------------------|
| JSON | [`plugin/jsonexport`](https://pkg.go.dev/github.com/hovsep/fmesh/plugin/jsonexport) | fmesh (bundled) | no |
| [Graphviz DOT](https://graphviz.org) | [`dot`](https://github.com/hovsep/fmesh-export/tree/main/dot) | [fmesh-export](https://github.com/hovsep/fmesh-export) | yes |
| [Mermaid](https://mermaid.js.org) | [`mermaid`](https://github.com/hovsep/fmesh-export/tree/main/mermaid) | [fmesh-export](https://github.com/hovsep/fmesh-export) | yes |
| [D2](https://d2lang.com) | [`d2`](https://github.com/hovsep/fmesh-export/tree/main/d2) | [fmesh-export](https://github.com/hovsep/fmesh-export) | yes |
| [PlantUML](https://plantuml.com) | [`plantuml`](https://github.com/hovsep/fmesh-export/tree/main/plantuml) | [fmesh-export](https://github.com/hovsep/fmesh-export) | yes |

- The output is deterministic: equal meshes give the same bytes.
- Exporting only reads the mesh. It never changes it.

Install a diagram exporter:

```bash
go get github.com/hovsep/fmesh-export/mermaid  # or /dot, /d2, /plantuml
```

## The shared API

All exporters have the same shape:

| Call | What it does |
|------|--------------|
| `New(opts...)` | Creates the plugin. Attach it with `fmesh.WithPlugins`. One plugin serves one mesh. |
| `Export()` | Returns the structure: components, ports, pipes, descriptions. |
| `WithCycles()` | Option. Records every cycle of the next run. Diagram exporters only. |
| `ExportCycles()` | Returns one diagram per cycle. Needs `WithCycles()`. Diagram exporters only. |
| `Export(fm, opts...)` | Package function. Exports a mesh built without the plugin. `jsonexport.Export(fm)` takes no options. |

## Static export

The shape is the same for every format. Mermaid as an example:

```go
import "github.com/hovsep/fmesh-export/mermaid"

exporter := mermaid.New()
fm, err := fmesh.New("mesh", fmesh.WithPlugins(exporter))
if err != nil {
    return err
}
// ... add components and pipes ...

src, err := exporter.Export()
if err != nil {
    return err
}
return os.WriteFile("mesh.mmd", src, 0o644)
```

Other formats change only the import and the `New` call:

| Format | Import | Plugin | Output |
|--------|--------|--------|--------|
| JSON | `github.com/hovsep/fmesh/plugin/jsonexport` | `jsonexport.New()` | indented JSON, also with metadata |
| DOT | `github.com/hovsep/fmesh-export/dot` | `dot.New()` | DOT source (`nil` for an empty mesh) |
| Mermaid | `github.com/hovsep/fmesh-export/mermaid` | `mermaid.New()` | Mermaid flowchart |
| D2 | `github.com/hovsep/fmesh-export/d2` | `d2.New()` | D2 source |
| PlantUML | `github.com/hovsep/fmesh-export/plantuml` | `plantuml.New()` | PlantUML component diagram |

Good component descriptions make the export document itself.

## One-off export

For a mesh built without the plugin, call the package function:

```go
data, err := jsonexport.Export(fm)
src, err := mermaid.Export(fm)
```

- `dot.Export`, `d2.Export` and `plantuml.Export` work the same way.
- The diagram exporters take the same options as `New`. `WithCycles()` has no effect here.
- `jsonexport.Export` takes no options.

## Per-cycle export

Create a diagram exporter with `WithCycles()`. It records every cycle of the next run. Then
`ExportCycles()` returns one diagram per cycle, in order. Each component is colored by its
activation result. It is a visual replay of the run.

```go
exporter := mermaid.New(mermaid.WithCycles())
fm, err := fmesh.New("mesh", fmesh.WithPlugins(exporter))
if err != nil {
    return err
}
// ... build and seed the mesh ...

if _, err := fm.Run(ctx); err != nil {
    return err
}
diagrams, err := exporter.ExportCycles()
if err != nil {
    return err
}
for i, d := range diagrams {
    if err := os.WriteFile(fmt.Sprintf("cycle-%03d.mmd", i+1), d, 0o644); err != nil {
        return err
    }
}
```

- The plugin records cycles itself, so `fmesh.WithCyclesHistoryLimit` does not shorten the replay.
- Default colors: green = OK, yellow/gold = no input, red = error, pink = panic, orange = hook
  failed, blue / purple = waiting (dropping / keeping inputs).
- The DOT graph also has a legend with the count of components in each state.

## Options

Each option sets one thing on top of the defaults. Anything you do not set keeps its default.

| Package | Options |
|---------|---------|
| `dot` | `WithAttrs(element, attrs)`, `WithResultAttrs(code, attrs)`, `WithComponentLabel(label)`, `WithCycles()` |
| `mermaid` | `WithDirection("TB")` (`LR` default), `WithResultColor(code, color)`, `WithCycles()` |
| `d2` | `WithDirection("down")` (`right` default), `WithResultColor(code, color)`, `WithCycles()` |
| `plantuml` | `WithDirection("top to bottom")` (`"left to right"` default), `WithResultColor(code, color)`, `WithCycles()` |
| `jsonexport` | none |

Each package README lists the details.

## Rendering

| Format | Command line | Online |
|--------|--------------|--------|
| DOT | `dot -Tsvg mesh.dot -o mesh.svg` ([Graphviz](https://graphviz.org)) | [edotor.net](https://edotor.net) |
| Mermaid | `mmdc -i mesh.mmd -o mesh.svg` ([mermaid-cli](https://github.com/mermaid-js/mermaid-cli)) | [mermaid.live](https://mermaid.live) |
| D2 | `d2 mesh.d2 mesh.svg` ([D2 CLI](https://d2lang.com/tour/install)) | [play.d2lang.com](https://play.d2lang.com) |
| PlantUML | `plantuml -tsvg mesh.puml` (needs Java) | [plantuml.com/plantuml](https://www.plantuml.com/plantuml) |

- **Mermaid** renders in GitHub and GitLab markdown. Put the source in a ` ```mermaid ` block, and
  the diagram can live in your README with no extra tools.
- **PlantUML** files also render in many IDEs and wikis with a PlantUML plugin.
- **Animation** of a per-cycle export: render each cycle to PNG, then join them, for example with
  ImageMagick: `convert -delay 100 -loop 0 cycle-*.png mesh.gif`.

## Tip: an export flag

The mesh is fully built before it runs. So you can put export behind an env variable or CLI flag:
build the mesh, write the diagram, and exit without running.

```go
if os.Getenv("MESH_GRAPH") == "1" {
    src, err := exporter.Export()
    if err != nil {
        return err
    }
    return os.WriteFile(fm.Name()+".mmd", src, 0o644)
}
_, err := fm.Run(ctx)
```

## Writing your own exporter

Implement `fmesh.Visitor` and call `fm.Walk`. `Walk` visits the mesh, then each component followed
by its input and output ports (all by name), then every pipe. Every port is visited before any pipe
that touches it, so an exporter can draw nodes first and edges after.

```go
type counter struct{ components, ports, pipes int }

func (c *counter) VisitMesh(*fmesh.FMesh) error                       { return nil }
func (c *counter) VisitComponent(*component.Component) error          { c.components++; return nil }
func (c *counter) VisitPort(*component.Component, *port.Port) error   { c.ports++; return nil }
func (c *counter) VisitPipe(from, to *port.Port) error                { c.pipes++; return nil }

var stats counter
err := fm.Walk(&stats)
```

Ship it as a plugin, like the exporters above: `Init` keeps the mesh, and `Export` walks it. For a
new diagram format, see
[Writing a new exporter](https://github.com/hovsep/fmesh-export#writing-a-new-exporter) in the
fmesh-export README.
