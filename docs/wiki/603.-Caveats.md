# 603. Caveats

Known trade-offs. None is a bug waiting for a fix: each follows from a design choice, and each is
easy to avoid once you know it.

---

## Outputs written before a wait are kept, and re-emitted

When a component waits, its output ports are not flushed and not cleared. What it wrote before
the wait stays there. When it later succeeds, the old and new signals flush together.

```go
component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
    if err := this.OutputByName("log").PutSignals(signal.New("attempt")); err != nil {
        return err
    }
    if !this.Inputs().AllHaveSignals() {
        return component.ErrWaitKeepingInputs
    }
    return this.OutputByName("out").PutSignals(signal.New("done"))
})
```

If this component waits once and then succeeds, downstream gets **two** `"attempt"` records.

**Why:** your code decides to wait, at any point, on any condition. The runtime cannot know in
advance that an activation will end in a wait.

**Fix:** decide first, then write.

```go
component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
    if !this.Inputs().AllHaveSignals() {
        return component.ErrWaitKeepingInputs // decide first
    }
    if err := this.OutputByName("log").PutSignals(signal.New("attempt")); err != nil {
        return err
    }
    return this.OutputByName("out").PutSignals(signal.New("done"))
})
```

When the condition is "these ports all have signals", use
`component.Sequential(component.RequireInputs("a", "b"), work)`. It does exactly this.

## Payloads are shared between destinations

Fan-out gives the **same `*Signal`** to every destination, and the destinations run concurrently.
Nothing copies the payload. Two components that change a received map race on the same map.

```go
// src fans out to w1 and w2
component.WithActivationFunc(func(ctx context.Context, this *component.Component) error {
    m, _ := this.InputByName("in").Signals().FirstAs[map[string]int]()
    m["n"]++ // DATA RACE: w1 and w2 hold the same map
    return this.OutputByName("out").PutSignals(signal.New(m))
})
```

**Why:** copying on every pipe would make fan-out cost grow with the data. And F-Mesh cannot copy
an `any` payload — it has no `Clone()`.

**Rule:** treat what you receive as read-only. Build **new** signals from it. Never change a
received map, slice or pointer.

```go
m, err := this.InputByName("in").Signals().FirstAs[map[string]int]()
if err != nil {
    return err
}
next := maps.Clone(m) // your copy
next["n"]++
return this.OutputByName("out").PutSignals(signal.New(next))
```

**Run your mesh tests with `-race`** (`go test -race ./...`). The race detector catches this one
reliably.

A payload with only one destination is safe today. Don't mutate it anyway: a second pipe added
later turns it into a race with no other code change.

## A stopping error discards its siblings' work

Under `StopOnFirstErrorOrPanic` (the default), the mesh checks whether to stop **before** it
drains. If one component fails and three succeed in the same cycle, the three outputs are never
flushed. They stay on the output ports.

**Why:** draining first would push a failed cycle's partial data downstream. Which is worse
depends on the mesh.

**Workaround:** when partial progress matters more than a clean stop, use `IgnoreAll` and handle
failures yourself:

```go
fm, err := fmesh.New("mesh", fmesh.WithErrorHandlingStrategy(fmesh.IgnoreAll))
```

Then find failures in `RuntimeInfo`, in a component `AfterActivation` hook, or through an error
output port piped to a handler component.

---

## Piping twice delivers twice

`PipeTo` does not check for an existing pipe. Piping the same output to the same input twice
creates two pipes, and every signal arrives **twice**:

```go
_ = out.PipeTo(in)
_ = out.PipeTo(in) // now every signal on out reaches in two times
```

This is on purpose: a pipe is an edge, and two edges carry two copies. Check before wiring when
the code that wires can run more than once:

```go
if !out.Pipes().Any(func(p *port.Port) bool { return p == in }) {
    err = out.PipeTo(in)
}
```

---

## A failed run leaves its inputs behind

When a run stops early, the inputs of its last cycle are not cleared. The next `Run` starts with
them, together with anything you seed. Clear the inputs first when a rerun must start clean — see
[Running a mesh again](https://github.com/hovsep/fmesh/wiki/401.-Scheduling-rules#running-a-mesh-again).

---

## Memory grows with cycles

`RuntimeInfo.Cycles` keeps **every** cycle of a run by default, with all activation results. The
default cycle limit of 1000 bounds it. If you remove that limit, add a history limit:

```go
fm, err := fmesh.New("mesh",
    fmesh.WithUnlimitedCycles(),
    fmesh.WithCyclesHistoryLimit(100), // keep the last 100 cycles
)
```

There is no backpressure either. Signals stay in memory for the whole run, so memory grows with
the amount of data you feed in.

---

## The time limit does not interrupt a component

Cancellation is cooperative. The time limit becomes a deadline on the context passed to
activation functions, and the mesh checks it between cycles. Go cannot stop a running goroutine,
so an activation function that ignores `ctx` runs past the limit and blocks the mesh until it
returns.

**Fix:** in slow or blocking code, pass `ctx` on (`http.NewRequestWithContext`, `select` on
`ctx.Done()`), or check `ctx.Err()` in long loops.

---

## Port lookups return nil

`ComponentByName`, `InputByName`, `OutputByName` and `Collection.ByName` return `nil` for an
unknown name, with no error. Calling a method on that nil port panics with `port.ErrNilPort`:

```go
this.OutputByName("outt").PutSignals(signal.New(1)) // the port is "out"
```

```
panicked: port is nil: InputByName, OutputByName and Collection.ByName return nil for a name no port has
```

- `Signals`, `HasSignals`, `PutSignals`, `PutPayloads` and `PutSignalGroups` panic this way.
- Inside an activation function the panic becomes an `ActivationCodePanicked` result. The run error
  names the component, and `errors.Is(err, port.ErrNilPort)` matches it. Outside an activation
  function (setup code), it panics outright.
- The message cannot name the port: a nil pointer has no name. Check the string you passed to the
  lookup.
- `PipeTo` is different: it returns `ErrNilPort` as a normal error.

Port names are strings and are not checked at wiring time. Ways to stay safe:

- check for `nil` when the name is not a constant:

  ```go
  if p := c.InputByName("data"); p != nil {
      // use p
  }
  ```

- keep names in constants:

  ```go
  const portIn = "in"
  component.WithInputs(portIn)
  this.InputByName(portIn)
  ```

- use the helpers that report the bad name: `component.RequireInputs`, `component.Pipeline`,
  `port.MultiPipe`, `port.MultiForward`. Prefer them over manual lookups.

---

## What is *not* a caveat

- **A mesh with no seeded inputs does nothing and returns `nil`.** Components activate only when
  an input has signals; there are no source components. Seed an input to start. See
  [401. Scheduling rules](https://github.com/hovsep/fmesh/wiki/401.-Scheduling-rules).
- **Hitting a limit returns an error.** `ErrReachedMaxAllowedCycles` and `ErrTimeLimitExceeded`
  mean the mesh was stopped, not that a component failed. Tell them apart with `errors.Is`.
  `ErrLivelockDetected` usually means a missing pipe; its message names the stuck components.
